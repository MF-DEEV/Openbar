# More session agents: Gemini CLI, Copilot CLI, OpenCode, Cursor, Pi, Mistral Vibe, Devin CLI, Google Antigravity, Grok CLI, ZCode, Hermes and Claude Desktop

Sessions lists every coding agent the person runs, not only Claude Code and Codex (issues #123, #220, #247, #243, #245, #244 and #246). Each agent below gets its own row in the shared list, its own mark, color and pixel figure, its count and mark in the closed island, and as much of the island's help as the agent allows. Each agent installed on the computer (its command, or Cursor's or Antigravity's app; a folder like `~/.gemini`, which other apps make, does not count) is connected by itself: the island adds its hooks or plugin next to the person's own, after a backup, when Sessions starts, when its settings change and whenever the agents are looked for, so one installed later is picked up. Turning the agent's switch off takes out only what the island added. Hermes is the one agent whose switch starts off, since Hermes asks the person to allow each new hook ([below](#hermes-244)).

## How the events reach the island

On the Mac each hook is the system's `nc` writing the agent's input, wrapped in an envelope, to the island's socket:

```
{ printf '{"openbar":"gemini","hook":"BeforeTool","pid":%d,"event":' "$PPID"; cat; printf '}'; } | /usr/bin/nc -U '<socket>' 2>/dev/null; exit 0 # openbar-hook <bundle>
```

On Windows the hook is the app itself, `Openbar.exe --hook --agent gemini --event BeforeTool`, which builds the same envelope (run with `&` under PowerShell for Gemini CLI and Cursor, and with Copilot's `exec` and `args`, which need no shell). When the island is not running the hook connects to nothing, prints nothing and exits 0, so the agent carries on as if there were no hook. The island finds the agent's own process by walking up from the hook's process past the shells, which tells it when the agent quits and which terminal shows it.

OpenCode's plugin (`AgentOpenCodePlugin.swift`, the same file as `windows/src-tauri/src/sessions/opencode-plugin.js`; a Rust test keeps them alike) runs inside OpenCode and writes envelopes of its own: `created`, `status`, `tool`, `permission`, `permissionReplied`, `message` (model, tokens, cost), `reply`, `title`, `deleted`. A `permission` envelope waits on its connection for `{"reply":"once"|"always"|"reject"}`, which the plugin hands to OpenCode with `client.postSessionIdPermissionsPermissionId`. A `listen` envelope waits for `{"prompt":{"session":…,"text":…}}`, which the plugin sends with `client.session.promptAsync`. Each time the plugin reaches the island anew, as after it restarts, it tells it of its sessions again.

## What was checked, and against what

- **Gemini CLI 0.66.0** (its `docs/hooks/reference.md` and bundle): `SessionStart`, `SessionEnd`, `BeforeAgent`, `AfterAgent`, `BeforeTool`, `AfterTool`, `Notification` with `notification_type: "ToolPermission"`. A `BeforeTool` hook can deny or force a prompt but not allow past the policy, and `Notification` is observability only, so its prompts are answered in the terminal. The hook's parent process is Gemini itself. Gemini takes a return that arrives with a paste as a line break, so a reply is pasted and sent by a return of its own half a second later. When a turn ends without text, `AfterAgent` carries `"[no response text]"`, which the island does not show. Run live on the Mac, with a `BeforeModel` hook answering in place of the model.
- **Copilot CLI 1.0.105** (docs.github.com, CLI hooks reference): camelCase events with `sessionId`, `notification` with `permission_prompt`. `permissionRequest` runs before Copilot's own rules and session approvals, so holding it in the island would ask for tools Copilot would have allowed; it is not installed. The account used here has no Copilot access, so its hooks were driven with the documented payloads through the installed hook file.
- **OpenCode 1.19.5** (`@opencode-ai/plugin` and `@opencode-ai/sdk` 1.19.5, and a logging plugin): the `permission.ask` hook is not called in this version; `permission.asked` and `permission.replied` events are, and replying through the SDK client works. In the TUI no HTTP server listens, so the plugin acts through its in-process client. Run live on the Mac with a free model: listing, Allow, Deny, a reply from the island, the island restarting.
- **Cursor** (cursor.com/docs/agent/hooks): a hook that may allow or deny an action blocks it when it answers with nothing, so only hooks that only tell are installed (`sessionStart`, `sessionEnd`, `beforeSubmitPrompt`, which answers `{"continue":true}`, `afterAgentThought`, `afterAgentResponse`, `postToolUse`, `postToolUseFailure`, `stop`). Cursor's app outlives its conversations, so one quiet for 30 minutes leaves the list. Not installed here; driven with the documented payloads through the installed hooks.

## Pi, Mistral Vibe and Devin CLI (#220)

- **Pi 1.5.2** (`@earendil-works/pi-coding-agent`, its `docs/extensions.md`): extensions are modules Pi loads in its own process, from `~/.pi/agent/extensions` (or `PI_CODING_AGENT_DIR`). The island's (`AgentPiExtension.swift`, the same file as `windows/src-tauri/src/sessions/pi-extension.js`; a Rust test keeps them alike) listens to `session_start`, `session_shutdown`, `before_agent_start`, `agent_start`, `agent_settled`, `tool_execution_start`/`_end`, `message_end` (model, usage, cost, reply), `model_select`, `session_info_changed` and `ui_prompt_start`/`_end`, and sends envelopes shaped like OpenCode's plugin's. Pi has no permission prompts of its own; `ui_prompt_start` fires when another extension opens a dialog, which shows as a wait answered in Pi. A `listen` envelope waits for a reply, which goes in through `pi.sendUserMessage` (as a follow-up while Pi works). Its sockets are unref'd so Pi quits when its work is done. Pi is taken as installed only with its `pi` command and its `~/.pi/agent` folder, since other tools take that name. Run live on the Mac against a stand-in model: listing, tools, cost, a reply from the island, an extension's dialog (Pi's own `permission-gate` example), Open, quitting; and in the Windows VM: listing, tools, cost, a reply from the island, announcing itself again after the island restarted. A connection that waits only writes: `end()` closes a Windows named pipe as a whole, which had left OpenCode's plugin unable to take an answer there too.
- **Mistral Vibe 3.1.2** (its bundled `vibe` skill, "Hooks"): `~/.vibe/hooks.toml` (or `VIBE_HOME`), `[[hooks]]` tables of `session_start` (with the model), `session_end`, `pre_agent`, `pre_tool`, `post_tool` and `notification` (`approval_requested`, `question_asked`, `turn_completed`, `turn_failed`). A hook can deny a tool but never approve one, so a hook alone leaves approvals to Vibe; the app server's callbacks answer them ([below](#answering-mistral-vibe-from-the-island-251)). `post_agent` runs after subagents' turns too, so turns end on `notification`; hooks carrying a `parent_session_id` are a subagent's and add no row. The island's tables go after the person's, between two marker lines, and a file keeping `hooks = [...]` inline is left alone. Hooks carry no reply text: with previews on, the last reply is read from the newest history chunk under the session's `transcript_path` (`chunks/*.json`). On Windows Vibe runs hooks in Git Bash when it is installed and otherwise PowerShell, so the command is this app's path with forward slashes and no quotes (its 8.3 form when it has a space), which Git Bash, PowerShell and `cmd /c` all run. Its terminal UI reads a console's keys, as Codex's does, so on Windows a reply goes in as plain keys rather than a bracketed paste, whose markers it would take as text. Run live on the Mac and in the Windows ARM64 VM (Vibe's x64 build under emulation) against a stand-in model: listing, tools, an approval waiting in Vibe, Open, the last reply, a reply from the island, `/exit`.
- **Devin CLI 3000.12.57** (docs.devin.ai, "Hooks" and "Lifecycle Hooks"): a local agent with its own login; hooks under `"hooks"` in `~/.config/devin/config.json` (`%APPDATA%\devin\config.json` on Windows), Claude Code's format and events (`SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PermissionRequest`, `Stop`). Payloads carry `session_id` and `prompt_id` but no folder, so the folder is the agent process's own. Devin's question to the person is its `ask_user_question` tool. A `PermissionRequest` hook could answer `{"decision": "approve"}`, but how Devin's own prompt behaves while a hook holds it could not be seen without a Devin account, so the island's hook only hears of the request and answers nothing, and Devin asks in its terminal. Devin also runs the hooks in Claude Code's settings (`read_config_from.claude`, on by default), so the island's Claude Code hooks run in Devin's sessions too; one is told apart by Devin's `prompt_id` with no `transcript_path`, or by Devin's process above the hook, and let go unanswered. No account was available: Devin's hooks were driven with the documented payloads through the installed hook commands from a process named `devin` (`devin.exe` run through `cmd /c` on Windows), on the Mac and in the Windows VM. Its replies are typed as plain keys on Windows too, as for Vibe, since its terminal UI is not known to take a bracketed paste there.

## Answering Mistral Vibe from the island (#251)

A session started with **New session** answers Mistral Vibe's approvals and questions in the island: Allow, Always (for the session) and Deny on the card, and the options of a question. Nothing is typed into the terminal, so it cannot break on a prompt or a key Vibe changes.

- **How Vibe's terminal UI works** (Vibe 3.1.2). `vibe` runs a Rust terminal UI (`vibe-rs`) on top of `vibe-app-server`: it starts the server as a child process and speaks JSON-RPC to it over the child's stdin and stdout, a message a line. The server's command comes from `VIBE_APP_SERVER_CMD` or `VIBE_APP_SERVER_BIN`; the `vibe` launcher clears both and sets its own, and takes another command only through `exec_rust_cli(app_server_cmd=…)` in its Python, which `vibe-acp` uses too.
- **The protocol.** An approval or a question is a request from the server to the client, `callback/call`, whose `callback.detail.kind` is `approval` or `user_input` (a connector's sign-in is a third). The client acknowledges it with `{"callbackId", "accepted": true}` and answers with a `callback/result` request: `{"sessionId", "result": {"callbackId", "output"}}`, where `output` is `{"type": "approval", "decision": {"type": "approve" | "approve_for_session" | "approve_permanently" | "deny" | "cancel_turn"}, "feedback"}` or `{"type": "user_input", "result": {"answers": [{"question", "answer", "isOther"}], "cancelled"}}`. The first answer wins: a second one comes back as the error `conflict`, and the server tells every client with `history/entryUpdated` that the callback's `/state` is no longer `open`. A client asks for these callbacks by listing `approval` and `user_input` in `callbackKinds` when it initializes.
- **The relay.** New session runs `<Vibe's Python> -I -c "…exec_rust_cli(…, app_server_cmd=[<Openbar>, --vibe-proxy, <hook socket>, <vibe-app-server>])" <prompt>`. The terminal UI starts, as it does from `vibe`, with the Openbar executable as its server: it starts Vibe's own `vibe-app-server`, passes every line both ways unchanged, and tells the island of the session (`attach`), of an approval or a question that needs an answer, and of one answered in the terminal (`settled`). It reaches the island on the same socket or pipe the hooks use, in the same envelope (`{"openbar": "vibe", "hook": "proxy", …}`), and the island answers on that connection, as OpenCode's plugin does. The relay answers the server with the `callback/result` and drops what comes back. Vibe's terminal UI does not close an approval's dialog when another client answers it, and keeps it open on the server's `conflict`; so the relay takes the terminal's own late `callback/result` for a callback the island answered and answers it `accepted` itself, and one Enter or Esc closes the dialog. (A question's widget closes on its own.) Nothing waiting for the island holds up the terminal UI: with the island not running, or nobody answering, Vibe asks in its terminal as before.
- **What stays in the terminal.** A session you start yourself runs the server in a pipe nothing can reach, so it stays as it was: hooks report it, an approval says to answer in the terminal, and a reply is typed there. It does when Vibe is not set up the way the launcher expects (no `vibe-app-server` beside `vibe`, no Python found beside it), and when the island is off. For a session through the relay Vibe's own `approval_requested` and `question_asked` hooks are dropped, since the relay tells of the same request with the means to answer it.
- **Checked live** with Vibe 3.1.2 against a stand-in model: an approval allowed, denied and allowed for the session from the island, one answered in the terminal first (the island's late answer is the server's `conflict`), a question answered from the island, a path of the Openbar executable with spaces and parentheses, and the island's card and strip.

## Google Antigravity (#247)

Checked against **Antigravity IDE 2.5.5** and **Antigravity 2.4.3** (the "Lifecycle Hooks" guide inside their language servers) and run live with **`agy` 1.5.9** on the Mac, Linux (Ubuntu 24.04 ARM64 VM) and Windows (Windows 11 ARM64 VM). Antigravity's app, its IDE and `agy` read the same global `~/.gemini/config/hooks.json` (and a workspace's `.agents/hooks.json`). Its top-level keys are named hooks; the island adds one of its own, named after the app (`openbar-<bundle id>`), beside the person's, after a backup, and Remove takes out every entry carrying the island's marker and nothing else.

- **Events.** `PreInvocation` and `PostInvocation` around each model call, `PreToolUse` and `PostToolUse` around each tool (grouped under a `"*"` matcher), and `Stop` when the turn ends. Input is camelCase: `conversationId` (the session), `workspacePaths`, `cwd`, `modelName` (as `gemini-3.8-flash-high`), `lastUserInput`, `transcriptPath`, and for tools `toolCall` (`name`, `args` such as `CommandLine`, `TargetFile`, `toolSummary`) with the `stepIdx` both ends share. There is no session, prompt or permission event: a turn starts at the invocation with `invocationNum` 0, whose `lastUserInput` is the prompt; `Stop` ends it (`terminationReason` is `NO_TOOL_CALL` for a turn that ended well).
- **Answers.** Every hook blocks Antigravity's loop, and a `PreToolUse` hook that prints `{}` refuses the tool call (seen live: "denied by a pre-tool hook"; CodeIsland reports the same for no output, a failure and a timeout). So the island's hook prints `{"decision":"ask"}` itself before anything else, island or not, which hands the call to Antigravity's own check with its grants and Always Allow, and `{}` for the other events. On the Mac that is a `printf` before `nc -w 2`; on Windows and Linux the app's `--hook` prints it first and gives the island two seconds at most. Antigravity runs hooks with `sh -c` (the app's path in single quotes) and `cmd /c` on Windows (the path with forward slashes and no quotes).
- **Approvals.** `allow` is documented, but CodeIsland reports it doesn't pass Antigravity's own permission check, and approving from the island would need Antigravity's undocumented local language-server API. So approvals stay in Antigravity. The hooks don't say when a call waits for the person, and the transcript writes a step only once it has run, so the row shows the tool as running and its hint says approvals stay in Antigravity.
- **Rows.** The process above the hook's shell is `agy` itself, or the language server of the Antigravity window, which outlives its conversations; a conversation quiet for 30 minutes leaves the list, as for Cursor. With previews on, the prompt comes from `lastUserInput` and the last reply from the `PLANNER_RESPONSE` steps at the end of `transcript_full.jsonl`.
- **Open and reply.** Open brings forward the IDE window showing the session's folder, the Antigravity app, or `agy`'s terminal. A reply is typed into `agy`'s terminal; the app's and IDE's agent panels take none, and the field says "Reply in Google Antigravity".
- **Verified live** on the Mac with a real `agy` turn (row, model, branch, running and done, the last reply with previews), and in the Linux VM: the hook going in beside a person's own and out alone, the row with model, branch and tools, working and done, a reply from the island reaching `agy` in tmux, the last reply with previews, the row leaving when `agy` quits, and a tool call still running with the island quit.

## Grok CLI (#243)

Checked against **Grok Build 1.0.89** (`@xai-official/grok`, xAI's own CLI, about 100k npm downloads a week; the community `grok-cli` has no hooks the island uses and isn't covered) and its user guide (`crates/codegen/xai-grok-pager/docs/user-guide/10-hooks.md` in xai-org/grok-build), and run live on the Mac against a stand-in model (a `[model.mock]` with an OpenAI-compatible `base_url` in `config.toml` starts Grok with no xAI sign-in).

- **Hooks.** Grok reads every `*.json` in `$GROK_HOME/hooks/` (`~/.grok/hooks/`, `%USERPROFILE%\.grok\hooks\` on Windows), so the island writes a file of its own, `openbar-<bundle id>.json`, and Remove takes that file out, a copy kept beside it under a name Grok doesn't read. Its events: `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PermissionDenied`, `Notification`, `Stop`, `StopFailure`, `StopCancelled`, each without a matcher (Grok refuses one on events that aren't a tool's) and with a 5-second timeout. Input is camelCase with snake_case event names (`hookEventName: "pre_tool_use"`), `sessionId`, `cwd`, `workspaceRoot`, `toolName`, `toolInput`, `toolUseId`, `lastAssistantMessage` on `Stop` and `transcriptPath` (`…/sessions/<folder>/<id>/updates.jsonl`). A custom model isn't named on `SessionStart`; the model comes from `current_model_id` in the session's `summary.json`, the only field read there. On the Mac the hook is the `nc` command; Grok runs it with `sh -c`. On Windows Grok runs a command with arguments through PowerShell (or Git Bash), so it is this app's path with forward slashes and no quotes.
- **A turn.** `UserPromptSubmit` opens it, `Stop` ends it with its last message, and `StopFailure` and `StopCancelled` (an interrupt, a refused prompt) end it without a done. As Grok quits it runs `Stop` once more with `reason: "shutdown"`, which ends nothing, beside `SessionEnd`, which takes the row away; a Grok that quits without it goes when its process does.
- **Approvals.** A hook can't approve: `allow` only means "not blocked" (the guide says so), and a hook that holds the call only delays Grok's own prompt. A prompt is told in two steps: the tool's `PreToolUse`, then a `Notification` with `notificationType: "permission_prompt"` and no tool in it, so the card shows the tool the session's last `PreToolUse` named, with its whole command or file and a file change's diff (Grok's `write` and `search_replace` take Claude Code's `Write` and `Edit` arguments), even with previews off. Grok's prompt starts on its plain "Yes" / "Yes, proceed", and its numbered options change from prompt to prompt (shell 2/3, file edit 2/3/4, more in a wide window), so the island never types a digit: **Allow** presses Return and **Deny** presses Ctrl+C, which closes the prompt and cancels the turn ("Turn cancelled because a permission prompt was dismissed"). The keys go to Terminal and iTerm2 on the Mac, Windows' console (Windows Terminal or conhost), WezTerm, zellij, tmux and kitty; where the island can't press keys (Ghostty, an editor's terminal, a remote host) the row says "Answer this one in Grok CLI." and Open takes the person there. A command Grok cut short (`toolInputTruncated`) can't be allowed from the island, as for Claude Code (#224). Answered in Grok's own terminal, the tool's `PostToolUse` (or `PermissionDenied`) ends the wait.
- **Questions.** Grok's `ask_user_question` tool (with an `elicitation_dialog` notification) shows as waiting, answered in Grok CLI: a pasted answer is taken as typed text rather than a choice there.
- **Claude Code's hooks.** Grok runs the hooks in `~/.claude/settings.json` too (`[compat.claude] hooks`, on by default), with its own input, so the island's Claude Code hooks run in Grok's sessions; one is told apart by `workspaceRoot` and the camelCase `hookEventName` no Claude Code hook input has, and let go unanswered.
- **Replies** are typed into its terminal; on Windows as plain keys, as for Vibe and Devin.
- **More than one config folder.** `GROK_HOME` names one; another can be added by hand on the Hooks page, as for Codex, Gemini, Copilot, Pi and Vibe.
- **Finding its process.** The island takes the process above the hook's shell as Grok's. On Windows Grok runs a hook through `powershell -Command`, which doesn't wait for this app (a windowed program), so that shell is often gone before the island looks; the island then reads the session's process from the `active_sessions.json` Grok keeps in its folder (`session_id`, `pid`), and nothing else from it.
- **Verified live** with a real `grok` against the stand-in model on all three systems. On the Mac in Terminal: the row with its model and tools, working, waiting and done, the card filled in from `PreToolUse`, **Allow** from the island running the command and **Deny** (Ctrl+C) cancelling the turn. In the Linux VM (Ubuntu 24.04 ARM64) in tmux: the hooks file going in by itself and out when the switch is turned off, the card, Allow, Deny, a reply from the island and the row leaving on `/quit`. In the Windows ARM64 VM in a console window: the same, with Allow and Deny pressed as console keys and the reply typed as plain keys.

## ZCode (#245)

Checked against ZCode's own source (github.com/zai-org/ZCode, Apache-2.0: `apps/zcode-cli` and the desktop app), the `zcode` CLI 0.17.1 built from it and the desktop app 3.18.2, run live against a stand-in model (a personal provider of type `openai-chat-completions` in `~/.zcode/v2/provider_config.json` starts ZCode with no Z.ai sign-in).

- **Hooks.** ZCode reads hooks only from `~/.zcode/cli/config.json`, under `hooks.events`, and runs none unless `hooks.enabled` is true (it is false by default); hooks in a project's `zcode.json` need ZCode's own trust step and aren't used. The desktop app runs its agent through the same runtime and the same file. Its events are `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PermissionRequest`, `PostToolUse`, `PostToolUseFailure` and `Stop`, and the file is checked strictly, so the island adds no other name. Each hook has a `timeoutMs`: 5 seconds, and 10 minutes for `PermissionRequest`. On the Mac the hook is the `nc` command, which ZCode runs with `/bin/sh`; on Windows and Linux it is a `process` hook, this app run with no shell between, so ZCode is its parent and waits for it. ZCode reads the hooks once as a session starts.
- **Input.** Claude Code's snake_case fields with ZCode's camelCase copies beside them: `session_id`, `cwd`, `tool_name`, `tool_input`, `tool_use_id`, `model` on `SessionStart` (`provider/model`; the island shows the model) and `last_assistant_message` on `Stop`. Its tools take Claude Code's names and arguments (`Bash`, `Read`, `Write`, `Edit`, `Grep`, `Glob`, `AskUserQuestion`; `ApplyPatch` reads as an edit), so a card reads as Claude Code's, with the whole command or a file change's diff even with previews off. The `transcript_path` it names is a temporary file of the hook's and isn't read.
- **Approvals.** ZCode runs the `PermissionRequest` hook while its own prompt is up, and whichever answers first wins (`permission-responder-race` in its runtime). The island's card answers with Claude Code's output, `hookSpecificOutput.decision.behavior` `allow` or `deny`; a hook that prints nothing or runs out of time just drops out, so the prompt in ZCode stays. Answered in ZCode first, ZCode stops the hook, and the tool's `PostToolUse` (or the turn's `Stop`) clears the card. Always isn't offered: ZCode's own "always allow in this project" rules aren't written from the island. ZCode asks only in its ask-first modes; in `yolo` and `guarded` no request reaches a hook.
- **Questions.** `AskUserQuestion` comes as a permission request too, and the island answers it with the question's own input and the answers in it (`updatedInput.answers`, one text per question). A question the island can't show is left to ZCode.
- **A session's end.** ZCode has no hook for it: a row goes when the session's process does.
- **The desktop app.** Its agent runs in processes of the app's own (`zcode-host-*`), so a session whose process sits under the app is the app's whatever terminal the app was started from: Open brings the app forward and no reply is typed anywhere. A task started there without a project runs in a folder of the app's own (`~/.zcode/workspace/default`, `draft-<id>`) and shows as **ZCode task**.
- **Process names.** ZCode renames its process (`zcode-cli`), which on the Mac writes over its arguments and zeros the rest of them; the island reads the environment after those zeros, which a session in tmux or zellij needs to be reached.
- **New session** doesn't offer ZCode: its terminal UI takes no first prompt, and `--prompt` runs without asking anything.
- **Replies** are typed into its terminal with one Return. A second Return, which other agents get a moment later, would land on a permission prompt the reply opens at once, where Return picks Deny (seen in the Windows and Linux VMs, and fixed there).
- **Verified live** with a real `zcode` built from source against the stand-in model on all three systems, and with the desktop app on the Mac and Windows. On the Mac in tmux and under a pty: the hooks going in next to nothing else and out when the switch is turned off, the row with its model and tools, the card, **Allow** and **Deny** from the island winning ZCode's prompt, an answer in ZCode clearing the card, a question answered from the island, a reply typed into tmux and the row leaving when ZCode quits. The desktop app's tasks show as **ZCode task**, are allowed from the island, take no reply and Open brings the app forward. In the Linux VM (Ubuntu 24.04 ARM64, tmux) and the Windows ARM64 VM (Windows Terminal), the same, with the hooks as `process` hooks; on Windows also the desktop app. ZCode's Linux desktop app wasn't run: it ships for x64 only, and the VM is ARM64.

## Hermes (#244)

Checked against Hermes Agent's source (github.com/NousResearch/hermes-agent, MIT) at **v0.23.3**, and run live from it against a stand-in model: `provider: custom` with a `base_url` in `config.yaml` starts Hermes with no account.

- **One gateway runs every session.** The classic terminal UI that `hermes` opens by default, its Ink UI (`hermes --tui`), its app and `hermes chat -q` all run their turns in a gateway Hermes starts in the background (`hermes gateway run --idle-exit`), and that gateway runs the shell hooks. A hook's parent is the gateway, its `cwd` is the gateway's folder and its environment is whoever started the gateway, so the island takes none of these for the session's. It reads the session's folder, source, title and model from Hermes's `state.db`, opened read only, and finds the session's terminal from the note Hermes's terminal client leaves for `hermes -c`: a file per terminal in `terminal-sessions/`, named after its device (`tty-dev-ttys004`, `tty-dev-pts-3`, or `wt_session-<id>` in Windows Terminal), holding the session's id. The client is the Hermes process on that terminal. A note stays after its session ends, and terminals are used again, so only the note of a session the island still lists counts; a new session's note is written a moment after its first hooks, and until then, as for its Ink UI, which writes no note, the island takes the only Hermes client in the session's folder that no other row claims, and looks again at the next hook. A session whose client isn't found is still listed, and goes when its client closes (`on_session_finalize`) or after 30 quiet minutes.
- **Hooks.** Shell hooks under `hooks:` in the `config.yaml` of Hermes's home (`HERMES_HOME`, else `~/.hermes`). Hermes splits a hook's command like a shell line and starts it with no shell, so on the Mac the island's line goes to `/bin/sh -c`, and on Windows and Linux the hook is this app itself. The island listens to eight events: `on_session_open`, `pre_llm_call` (the prompt and the model), `pre_tool_call`, `post_tool_call`, `on_session_end` (each turn's end, completed, failed or interrupted), `on_human_input_request` and `on_human_input_resolved` (a dangerous command, a question or a password waiting on the person) and `on_session_finalize` (the client closed). Each of the island's entries is a line of its own under its event, after the person's own entries, and a key the island adds carries its marker as a comment. Hermes reads the file with a parser that refuses a key twice, so the island joins an existing `hooks:` mapping. Remove takes only the island's lines, and a key it added or emptied. Hooks written inline (`hooks: {…}` with entries in it) are left alone, and the agent shows as unreadable.
- **Hermes asks before it runs a new hook.** A foreground `hermes` prompts once for each event and command (`Allow this hook to run? [y/N]`) and keeps the answers in `shell-hooks-allowlist.json`. Its gateway, its app and cron never ask, and skip a hook nobody allowed. The island doesn't write that allowlist and doesn't touch `hooks_auto_accept`. Because of this step Hermes's switch starts off. Turning it on adds the hooks, and the line under the switch reads the allowlist and says how many of the island's hooks Hermes hasn't been allowed to run yet: answer `y` to each prompt in `hermes`, or start it once with `hermes --accept-hooks`, which allows every hook configured at that moment. A changed command (another socket, the app moved) needs allowing again.
- **Answers go through Hermes's gateway.** A Hermes hook can block a tool but can't let one past Hermes's own check, so the island answers the way Hermes's Ink UI and app do. `hermes gateway attach --json` prints a one-use ticket for the gateway's WebSocket on `127.0.0.1`. The island joins the session as one more viewer (`session.resume`, which lists the prompts waiting), answers and leaves. Joining fires `on_session_open` again with `reason: resume`, which the island doesn't take as a new client.
- **Approvals.** Before a dangerous command Hermes shows a menu: Allow once (picked first), Allow for this session, Add to permanent allowlist and Deny, then View in the classic terminal UI when the command is longer than 70 characters. The island shows the command as Hermes's prompt shows it, secrets masked. Allow answers `once` and Deny `deny` through `approval.respond`, and Hermes's Ink UI and app close their card by themselves. Its classic terminal UI keeps its menu up after an answer from elsewhere, so there the island presses keys in the session's terminal where it can (Terminal, iTerm2, tmux, zellij, WezTerm, kitty, Windows' console): Return for Allow once, three down arrows and Return for Deny. The arrows stop at the last choice, so they reach Deny whichever choices are offered, except when View follows a shorter list. In a terminal the island can't press keys in, the gateway answers and the stale menu stays until a key is pressed.
- **Questions.** A `clarify` call asks one to five questions, each with up to four choices, one pick or several, or none for a free answer. They all show on the card, with an answer of one's own and Skip. The gateway holds them as a request of its own (`open_requests`), and the island locks each answer with `clarify.lock`: one pick as text, several as a list, a skipped question as nothing. The last lock settles it, and every Hermes client, its classic terminal UI too, closes its card. A sudo or vault password is still typed in Hermes.
- **Replies** are typed into a terminal session's terminal with a single Return. A second one would pick Allow once on a menu the reply may open.
- **Chats its gateway answers** on Telegram, Discord, Slack, WhatsApp and the rest aren't listed: their `source` in `state.db` names the platform, and only terminal, Ink UI, app, `chat -q` and ACP sessions are listed. They have no window to open and go on long after anyone looks.
- **Profiles.** Only the default profile's `config.yaml` gets the hooks; a session of another profile (`hermes -p <name>`) isn't listed.
- **Windows.** Hermes runs natively on Windows (its `install.ps1` and an MSIX app), not only in WSL. There its note names the Windows Terminal tab (`wt_session-<id>`), which the island matches against `WT_SESSION` in the environment of `hermes.exe` and the Python running it.
- **New session** starts `hermes chat -q '<prompt>'`, which on a terminal opens an interactive session with the prompt as its first turn.
- **Verified live** with Hermes v0.23.3 from source against the stand-in model. On the Mac in tmux: the eight consent prompts, the row with its title, folder, branch and model, working, waiting and done, Allow and Deny on a dangerous command, a reply from the island, and the row leaving on `/quit`. Later, on the Mac with the island's clicks: Allow and Deny in its Ink UI through the gateway; two questions, one of them with several picks, answered in its Ink UI; Skip in its Ink UI; an answer of one's own to a free question in its classic terminal UI; and Deny with keys there. The Rust client (Windows and Linux) answered the same gateway from a test: Deny in the Ink UI, and two questions with one skipped. In the Linux VM (Ubuntu 24.04 ARM64) in tmux: the hooks going into `config.yaml` by themselves with a backup, the same card, Allow, Deny, the question and the reply, the row leaving on `/quit`, and a working session leaving when its terminal was closed without `/quit`. Not run yet: Windows, Hermes's app, and a real model.

## Claude Desktop (#246)

Read from **Claude Desktop 1.24012.9 and 6.6395.1** for macOS (their `app.asar`) and Anthropic's docs for the app's third-party mode, and run live on the Mac with **Claude Desktop 6.6395.1** (its bundled Claude Code 2.1.326) in third-party mode against a stand-in model, with no account signed in. There's no Claude Desktop for Linux.

- **Code tab.** The app runs Claude Code through the Agent SDK with `settingSources: ["user", "project", "local"]`, so the hooks in `~/.claude/settings.json`, the island's among them, run there as in a terminal, and Claude Code writes its `~/.claude/sessions/<pid>.json` record and its transcript in `~/.claude/projects/` as usual. The app sets `CLAUDE_CODE_ENTRYPOINT` to `claude-desktop`, or `claude-desktop-3p` with third-party inference, and Claude Code copies it into the record's `entrypoint`; that is how the island tells these sessions apart. Their rows keep Claude's mark and color and get a **Desktop** label; the app is their host, so nothing is ever typed into a terminal for them. Nothing is installed for them: the island's Claude Code hooks are all they need, and Install and Remove are unchanged.
- **Approvals in the Code tab.** The app asks for a permission through the SDK's `canUseTool`. Claude Code runs its `PermissionRequest` hooks beside that, as it does beside its terminal dialog: the first answer wins, and when a hook answers, Claude Code sends the app `control_cancel_request` for its own request. Seen live: Allow on the island's card ran the command and the app's own "Allow Claude to run this command?" box went away by itself. So the card in the island answers these sessions too, questions included.
- **Open.** The app knows a session by its own id, `local_<uuid>`: a Cowork session's file is named after it, and for a Code tab session the island finds it in the record the app keeps, `claude-code-sessions/<account>/<org>/local_<id>.json`, by its `cliSessionId` (the only two fields read there). Open then opens `claude://code/needs-input?session=local_<id>`, which Claude Desktop 6 takes to that Code tab or Cowork session, and brings the app forward when it has no link. The app follows these links only for a signed-in account: in third-party mode it logs "code entry deep link ignored (entry points off)" and Open just brings it forward, which is what the live run showed (the link arrived and was set aside). `claude://resume?session=<id>`, the link `/desktop` uses, isn't used: it imports a Claude Code session into the app, a second time for one that's already there.
- **Replies.** The app has no terminal to type into, and Claude Code's peer socket labels what it delivers as not from the person, so the reply field says "Reply in Claude Desktop".
- **Cowork.** The app runs Cowork's Claude Code inside its own virtual machine with `CLAUDE_CODE_ENTRYPOINT=local-agent` and a config folder of its own per session, so no hook of the island's runs there. The app keeps, per session, `local-agent-mode-sessions/<account>/<org>/local_<id>.json` (`title`, `userSelectedFolders`, `model`, `createdAt`, `lastActivityAt`, `isArchived`, and more the island doesn't read) and a folder for the session, named after the first part of its id in Claude Desktop 6 (`2e916da8` for `local_2e916da8-…`), with `audit.jsonl`: every message of the session as the SDK streams it (`user`, `assistant`, `result`, `system`), and the app's own `permission_request` and `permission_response` lines with a `uuid` each, all stamped with `_audit_timestamp`. With **Read Cowork sessions** on, the island reads those two files, never writes them, from `~/Library/Application Support/Claude` and `Claude-3p` on the Mac, and on Windows from `%APPDATA%\Claude`, `%LOCALAPPDATA%\Claude-3p` and the same two inside the Store package's `LocalCache`. The island never looks inside a session's folder otherwise: it holds the person's uploads and outputs. A prompt opens a turn (the app logs it twice, as it replays it to the session), a tool call runs, a `permission_request` without its `permission_response` waits on the person (`AskUserQuestion` as a question), and `result` ends the turn. A session shows only while the app runs and while it's working or waiting, or was active in the last 10 minutes; an archived one never does, and a turn nobody heard from for 30 minutes is no longer working, since the app writes nothing when it stops mid-turn. Approvals, questions and replies stay in Claude Desktop: the row says "Answer this one in Claude Desktop." and Open brings the app forward, as Cowork has no link to one session. The title, prompts, replies and tool arguments are kept only with Show previews on; with previews off the row is named after its folder.
- **Settings.** Claude Desktop has two switches under More agents, shown only where the app is installed: Code tab sessions (on), and Read Cowork sessions (off until turned on). With the first off, Code tab sessions leave the list and their hooks are let go unanswered, so the app asks as it would without the island.
- **Tested without an account.** Claude Desktop's third-party mode (`inferenceProvider: gateway` with a local stand-in model) needs no sign-in and keeps its data in `Claude-3p`, apart from a signed-in app's. Run live on the Mac (Claude Desktop 6.6395.1) and in the Windows 11 ARM64 VM (the Store package, 5.11492.5, whose data is in `%LOCALAPPDATA%\Claude-3p`): a Code tab session listed with its Desktop label, Allow on the island running the command and closing the app's own prompt, the reply field pointing at the app; a Cowork session listed working, waiting on a question ("Answer this one in Claude Desktop.") and done once answered in the app. Cowork ran in both without its virtual machine (the app falls back to running on the computer), which writes the same files.

## Limits

- None of these agents keeps a registry the island could read, so a Gemini CLI, Copilot CLI or Cursor session that was already running when the island started shows up at its next event. OpenCode's plugin announces its sessions itself.
- Gemini CLI says nothing when a permission prompt is answered no; the row waits until the agent's next event.
- A file change's diff shows for OpenCode (from the permission's `metadata.diff` or `metadata.files`, which the plugin passes on) and for Gemini CLI (from its edit confirmation's `originalContent`/`newContent`, or `fileDiff`), above where to answer it. Copilot CLI's permission notice carries only a message and Cursor's approvals stay in Cursor, so neither shows one.
- Usage and cost for Gemini CLI and Cursor in AI Agents are out of scope (#123), and for Pi, Mistral Vibe and Devin CLI too (#220); Pi's cost shows on its session.
- Answering Devin CLI's permission prompts in the island waits on a live check of its `PermissionRequest` hook with a Devin account.
- Grok CLI's questions are answered in Grok CLI, and its approvals too where the island can't press keys in its terminal.
- Hermes's hooks run only once the person allowed them in Hermes, a sudo or vault password is typed in Hermes, and only its default profile is listed.
- Cowork's approvals, questions and replies are answered in Claude Desktop, and Open can't take the person to one Cowork session, only to the app.
- Google Antigravity's rows have no "waiting for you" state, since neither its hooks nor its transcript tell of a pending approval; and a conversation already running when the island started shows up at its next event.
