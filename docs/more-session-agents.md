# More session agents: Gemini CLI, Copilot CLI, OpenCode, Cursor, Pi, Mistral Vibe and Devin CLI

Sessions lists every coding agent the person runs, not only Claude Code and Codex (issues #123 and #220). Each agent below gets its own row in the shared list, its own mark, color and pixel figure, its count and mark in the closed island, and as much of the island's help as the agent allows. Each agent installed on the computer (its command, or Cursor's app; a folder like `~/.gemini`, which other apps make, does not count) is connected by itself: the island adds its hooks or plugin next to the person's own, after a backup, when Sessions starts, when its settings change and whenever the agents are looked for, so one installed later is picked up. Turning the agent's switch off takes out only what the island added.

## What each agent reaches

| Agent | Channel | Visible | Open | Approve | Reply | Details |
|---|---|---|---|---|---|---|
| Gemini CLI | hooks in `~/.gemini/settings.json` | yes | its terminal | in Gemini CLI | typed into its terminal | tools, last reply |
| Copilot CLI | a hooks file in `~/.copilot/hooks/` | yes | its terminal | in Copilot CLI | typed into its terminal | tools |
| OpenCode | a plugin in `~/.config/opencode/plugins/` | yes | its terminal | **in the island** (once, always, reject) | **in the island**, through the plugin | tools, model, tokens, cost, title, last reply |
| Cursor (app and `cursor-agent`) | hooks in `~/.cursor/hooks.json` | yes | Cursor, or `cursor-agent`'s terminal | in Cursor | `cursor-agent` in a terminal only | tools after they run, model, last reply |
| Pi | an extension in `~/.pi/agent/extensions/` | yes | its terminal | none to answer: Pi asks no permissions; another extension's dialog is answered in Pi | **in the island**, through the extension | tools, model, tokens, cost, title, last reply |
| Mistral Vibe | entries in `~/.vibe/hooks.toml`, between the island's markers | yes | its terminal | in Mistral Vibe | typed into its terminal | tools, model, last reply (from its session log, previews on) |
| Devin CLI | hooks in `~/.config/devin/config.json` (`%APPDATA%\devin\config.json` on Windows) | yes | its terminal | in Devin CLI | typed into its terminal | tools |

Where the island can't answer a request, the card says "Answer this one in Gemini CLI." (or the agent's name) and **Open** takes the person there.

## How the events reach the island

On the Mac each hook is the system's `nc` writing the agent's input, wrapped in an envelope, to the island's socket:

```
{ printf '{"openbar":"gemini","hook":"BeforeTool","pid":%d,"event":' "$PPID"; cat; printf '}'; } | /usr/bin/nc -U '<socket>' 2>/dev/null; exit 0 # openbar-hook <bundle>
```

On Windows the hook is the app itself, `Openbar.exe --hook --agent gemini --event BeforeTool`, which builds the same envelope (run with `&` under PowerShell for Gemini CLI and Cursor, and with Copilot's `exec` and `args`, which need no shell). When the island is not running the hook connects to nothing, prints nothing and exits 0, so the agent carries on as if there were no hook. The island finds the agent's own process by walking up from the hook's process past the shells, which tells it when the agent quits and which terminal shows it.

OpenCode's plugin (`AgentOpenCodePlugin.swift`, the same file as `windows/src-tauri/src/sessions/opencode-plugin.js`; a Rust test keeps them alike) runs inside OpenCode and writes envelopes of its own: `created`, `status`, `tool`, `permission`, `permissionReplied`, `message` (model, tokens, cost), `reply`, `title`, `deleted`. A `permission` envelope waits on its connection for `{"reply":"once"|"always"|"reject"}`, which the plugin hands to OpenCode with `client.postSessionIdPermissionsPermissionId`. A `listen` envelope waits for `{"prompt":{"session":…,"text":…}}`, which the plugin sends with `client.session.promptAsync`. Each time the plugin reaches the island anew, as after it restarts, it tells it of its sessions again.

## What was checked, and against what

- **Gemini CLI 0.66.0** (its `docs/hooks/reference.md` and bundle): `SessionStart`, `SessionEnd`, `BeforeAgent`, `AfterAgent`, `BeforeTool`, `AfterTool`, `Notification` with `notification_type: "ToolPermission"`. A `BeforeTool` hook can deny or force a prompt but not allow past the policy, and `Notification` is observability only, so its prompts are answered in the terminal. The hook's parent process is Gemini itself. Gemini takes a return that arrives with a paste as a line break, so a reply is pasted and sent by a return of its own half a second later. When a turn ends without text, `AfterAgent` carries `"[no response text]"`, which the island does not show. Run live on the Mac, with a `BeforeModel` hook answering in place of the model.
- **Copilot CLI 1.0.105** (docs.github.com, CLI hooks reference): camelCase events with `sessionId`, `notification` with `permission_prompt`. `permissionRequest` runs before Copilot's own rules and session approvals, so holding it in the island would ask for tools Copilot would have allowed; it is not installed. The account used here has no Copilot access, so its hooks were driven with the documented payloads through the installed hook file.
- **OpenCode 1.19.5** (`@opencode-ai/plugin` and `@opencode-ai/sdk` 1.19.5, and a logging plugin): the `permission.ask` hook is not called in this version; `permission.asked` and `permission.replied` events are, and replying through the SDK client works. In the TUI no HTTP server listens, so the plugin acts through its in-process client. Run live on the Mac with a free model: listing, Allow, Deny, a reply from the island, the island restarting.
- **Cursor** (cursor.com/docs/agent/hooks): a hook that may allow or deny an action blocks it when it answers with nothing, so only hooks that only tell are installed (`sessionStart`, `sessionEnd`, `beforeSubmitPrompt`, which answers `{"continue":true}`, `afterAgentThought`, `afterAgentResponse`, `postToolUse`, `postToolUseFailure`, `stop`). Cursor's app outlives its conversations, so one quiet for 30 minutes leaves the list. Not installed here; driven with the documented payloads through the installed hooks.

## Pi, Mistral Vibe and Devin CLI (#220)

- **Pi 1.5.2** (`@earendil-works/pi-coding-agent`, its `docs/extensions.md`): extensions are modules Pi loads in its own process, from `~/.pi/agent/extensions` (or `PI_CODING_AGENT_DIR`). The island's (`AgentPiExtension.swift`, the same file as `windows/src-tauri/src/sessions/pi-extension.js`; a Rust test keeps them alike) listens to `session_start`, `session_shutdown`, `before_agent_start`, `agent_start`, `agent_settled`, `tool_execution_start`/`_end`, `message_end` (model, usage, cost, reply), `model_select`, `session_info_changed` and `ui_prompt_start`/`_end`, and sends envelopes shaped like OpenCode's plugin's. Pi has no permission prompts of its own; `ui_prompt_start` fires when another extension opens a dialog, which shows as a wait answered in Pi. A `listen` envelope waits for a reply, which goes in through `pi.sendUserMessage` (as a follow-up while Pi works). Its sockets are unref'd so Pi quits when its work is done. Pi is taken as installed only with its `pi` command and its `~/.pi/agent` folder, since other tools take that name. Run live on the Mac against a stand-in model: listing, tools, cost, a reply from the island, an extension's dialog (Pi's own `permission-gate` example), Open, quitting; and in the Windows VM: listing, tools, cost, a reply from the island, announcing itself again after the island restarted. A connection that waits only writes: `end()` closes a Windows named pipe as a whole, which had left OpenCode's plugin unable to take an answer there too.
- **Mistral Vibe 3.1.2** (its bundled `vibe` skill, "Hooks"): `~/.vibe/hooks.toml` (or `VIBE_HOME`), `[[hooks]]` tables of `session_start` (with the model), `session_end`, `pre_agent`, `pre_tool`, `post_tool` and `notification` (`approval_requested`, `question_asked`, `turn_completed`, `turn_failed`). A hook can deny a tool but never approve one, so approvals stay in Vibe. `post_agent` runs after subagents' turns too, so turns end on `notification`; hooks carrying a `parent_session_id` are a subagent's and add no row. The island's tables go after the person's, between two marker lines, and a file keeping `hooks = [...]` inline is left alone. Hooks carry no reply text: with previews on, the last reply is read from the newest history chunk under the session's `transcript_path` (`chunks/*.json`). On Windows Vibe runs hooks in Git Bash when it is installed and otherwise PowerShell, so the command is this app's path with forward slashes and no quotes (its 8.3 form when it has a space), which Git Bash, PowerShell and `cmd /c` all run. Its terminal UI reads a console's keys, as Codex's does, so on Windows a reply goes in as plain keys rather than a bracketed paste, whose markers it would take as text. Run live on the Mac and in the Windows ARM64 VM (Vibe's x64 build under emulation) against a stand-in model: listing, tools, an approval waiting in Vibe, Open, the last reply, a reply from the island, `/exit`.
- **Devin CLI 3000.12.57** (docs.devin.ai, "Hooks" and "Lifecycle Hooks"): a local agent with its own login; hooks under `"hooks"` in `~/.config/devin/config.json` (`%APPDATA%\devin\config.json` on Windows), Claude Code's format and events (`SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PermissionRequest`, `Stop`). Payloads carry `session_id` and `prompt_id` but no folder, so the folder is the agent process's own. Devin's question to the person is its `ask_user_question` tool. A `PermissionRequest` hook could answer `{"decision": "approve"}`, but how Devin's own prompt behaves while a hook holds it could not be seen without a Devin account, so the island's hook only hears of the request and answers nothing, and Devin asks in its terminal. Devin also runs the hooks in Claude Code's settings (`read_config_from.claude`, on by default), so the island's Claude Code hooks run in Devin's sessions too; one is told apart by Devin's `prompt_id` with no `transcript_path`, or by Devin's process above the hook, and let go unanswered. No account was available: Devin's hooks were driven with the documented payloads through the installed hook commands from a process named `devin` (`devin.exe` run through `cmd /c` on Windows), on the Mac and in the Windows VM. Its replies are typed as plain keys on Windows too, as for Vibe, since its terminal UI is not known to take a bracketed paste there.

## Limits

- None of these agents keeps a registry the island could read, so a Gemini CLI, Copilot CLI or Cursor session that was already running when the island started shows up at its next event. OpenCode's plugin announces its sessions itself.
- Gemini CLI says nothing when a permission prompt is answered no; the row waits until the agent's next event.
- A file change's diff shows for OpenCode (from the permission's `metadata.diff` or `metadata.files`, which the plugin passes on) and for Gemini CLI (from its edit confirmation's `originalContent`/`newContent`, or `fileDiff`), above where to answer it. Copilot CLI's permission notice carries only a message and Cursor's approvals stay in Cursor, so neither shows one.
- Usage and cost for Gemini CLI and Cursor in AI Agents are out of scope (#123), and for Pi, Mistral Vibe and Devin CLI too (#220); Pi's cost shows on its session.
- Answering Devin CLI's permission prompts in the island waits on a live check of its `PermissionRequest` hook with a Devin account.
