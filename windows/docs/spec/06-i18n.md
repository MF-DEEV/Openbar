## 1. How strings are stored in Swift

There are no `.strings`, `.stringsdict` or `.xcstrings` catalogs for the UI, and no `NSLocalizedString` calls (`grep` finds 0). The only `*.lproj` folders hold `InfoPlist.strings`: macOS permission-prompt texts that Windows doesn't need. **Every UI string is a Swift string literal in a struct initializer**, checked by the compiler: adding a field forces every language to provide it (`LOC:150-152`).

### 1.1 The main catalog: `Strings` (accessed as `l10n.s.<field>`)
* `struct Strings { let statusIdleTooltip: String … }` declares **1,074** `String` fields, grouped by `// MARK:` comments (`LOC:153-1319`). A few trailing comments document arguments, e.g. `let shelfSelectedFormat: String // + count`.
* The language tables are `extension Strings { static let <lang> = Strings(field: "…", …) }`:
  * `ptBR` sits in `LOC:1321-2431` and `enUS` in `LOC:2433-3543`.
  * The other 13 languages each have a file in `LOCS/` (e.g. `LOCS/Strings+Ukrainian.swift:7-8` starts `static let uk = Strings(`).
* `Strings.localized(_:)` maps every `AppLanguage` to its static table (`LOC:127-149`).

### 1.2 Feature tables: `FeatureStrings.<accessor>(language)`
`enum FeatureStrings {}` (`FS:6`) is a namespace. Each feature adds a struct plus an accessor. The extractor finds 70 `FeatureStrings` accessors, plus 8 tables reached only through their own type's `localized(_:)` (GraphScale, NotchLowBattery, PointerDisplay, MediaImageConverter, ShelfPromiseDelivery, WhatsAppOrganizer, WindowDirectional, SettingsNavigation; the last is declared `-> Self` / `return Self(…)`). The source uses **six shapes**, and a parser must handle all of them:

| Shape | Example |
|---|---|
| A. Inline per case | `NFS:25-45`: `case .enUS: return NotchFilesStrings(archive: "Create ZIP", …)` |
| B. Case → static table | `NS:101-120` + `NS:122-`: `case .enUS: return .enUS` and `extension NotchStrings { static let enUS = NotchStrings(…) }` |
| C. Static tables **inside the struct body** | `FS:477-541`: `struct ClipboardFeatureStrings { let …; static let enUS = ClipboardFeatureStrings(…) }`; `FS:112-140` (Mixer) holds a whole table on **one line** |
| D. `.init(` one-liners | `Core/GraphScaleStrings.swift:9-23`: `case .enUS: return .init(title: "Show graph scale")` |
| E. Aliases and multi-case | `Core/CPUCoreStrings.swift:34`: `case .zhTW, .zhHK: return .zhTW`; English-only: `Core/NotchClaudeSessionStrings.swift:135-140` (`case .enUS, .ptBR, … .zhHK: return .enUS`) |
| F. Delegation and builders | `FS:107-109`: `WhatsAppDownloadStrings.localized(language)`. `Core/WhatsAppDownloadStrings.swift:536-560` builds 10 languages through a private function `translated(language:title:hub:…)` that mixes arguments with another table. |

Other facts that matter for extraction:
* **Case order varies by file**: `enUS, ptBR, es, sk, de, …` in `NFS`, versus the enum order in others. Key by the case label, never by position.
* **Non-string members exist.** There are dictionary fields such as `let shells: [ClawdShell: String]`, written as `[.clay: "Clay", …]`. Some structs also contain helper functions that are code, not data: `func dressUp(_ name: String) -> String { String(format: dressUpFormat, name) }` and `func name(_ shell:)` (`Core/NotchClaudeSessionStrings.swift:125-130`). Port the helpers as TypeScript functions over the JSON.
* The literals use only plain `"…"` strings with `\"`, `\\`, `\n` and `\u{…}` escapes. There are **no** `"""` multi-line literals and **no** string interpolation `\(…)` inside the tables (the extractor reports 0). The `#` characters found in some files are text inside ordinary strings (e.g. `"Copier sans le préfixe #"`), not raw-string delimiters.
* Some strings are concatenated or interpolated **in view code**, not in the tables: e.g. `"\(text.archive) · \(count)"` (`UI/Notch/NotchFilesView.swift:232`), `"\(text.imageEntryLabel) · \(entry.imageDimensionsLabel)"` (`UI/Notch/NotchClipboardView.swift:612`). The React components have to rebuild these from the same pieces.

## 3. How the language is chosen

* `L10n.shared` is an `ObservableObject` with `@Published var language: AppLanguage` (`LOC:108-125`). Views read `l10n.s` or `FeatureStrings.x(l10n.language)`, so a change re-renders the whole UI at once, with no restart.
* It is persisted in `UserDefaults` under `appLanguage` (`DEF:10`), as the raw value. There is no registered default: when the key is missing, `AppLanguage.systemDefault` is used.
* **First-launch system default** (`LOC:84-103`), from `Locale.preferredLanguages.first` (fallback `"en"`):
  1. Lowercased value starts with `zh-hk` or `zh-hant-hk` → `zhHK`.
  2. Starts with `zh-tw`, `zh-hant-tw` or `zh-hant` → `zhTW`.
  3. Otherwise the first matching prefix on the original value, in order: `pt`→ptBR, `tr`, `ru`, `es`, `sk`, `de`, `fr`, `it`, `ja`, `ko`, `uk`, `zh`→zhHans.
  4. Otherwise `enUS`.
* The user can change it in Settings → General (a picker over `AppLanguage.allCases` bound to `l10n.language`, `UI/Settings/GeneralSettings.swift:79-81`) and in onboarding (`UI/Onboarding/OnboardingView.swift:164`).
* **Dates and times** use `language.formattingLocale()` (`LOC:77-82`): the language's identifier combined with the **system's** region, hour cycle (12/24 h) and first weekday. Example: the clipboard card date is `.dateTime.month(.abbreviated).day().hour().minute()` in that locale (`UI/Notch/NotchClipboardView.swift:449-450`).

**Windows equivalent**
* System default: `GetUserPreferredUILanguages(MUI_LANGUAGE_NAME)` (or the `sys-locale` crate) in Rust, mapped with the same rules. Windows reports e.g. `zh-TW`, `zh-HK`, `zh-CN`, `pt-BR` and `pt-PT`; `pt-PT` maps to ptBR, as on the Mac.
* Persist `appLanguage` in the app settings store, using the same raw values.
* In React: a `LanguageContext` providing `lang` and `t(accessor, key)`. Changing it re-renders everything, matching the Mac.
* Formatting locale: build `new Intl.DateTimeFormat(lang, { hourCycle })`. Read the region from `GetUserDefaultLocaleName` / `GetUserDefaultGeoName`, 12/24 h from `GetLocaleInfoEx(LOCALE_NAME_USER_DEFAULT, LOCALE_STIMEFORMAT)`, and the first day of the week from `LOCALE_IFIRSTDAYOFWEEK`. Pass them from Rust once at startup and on `WM_SETTINGCHANGE` ("intl"). Combine as `<lang>-<region>`, e.g. `de-PL`, with `hourCycle` set explicitly. Intl falls back gracefully when the combination is unusual.

## 5. Format strings and plurals

### 5.1 `String(format:)` placeholders
Specifiers found across all extracted values, **summed over all 15 languages** (divide by about 15 for one language; en-US alone has 134 `%@`):

| Specifier | Occurrences | Meaning |
|---|---|---|
| `%@` | 1,980 | string argument |
| `%d` | 1,178 | integer (slightly inflated: includes the `%d` tokens in the file-name pattern help, see `%s`) |
| `%1$d`, `%2$d`, `%3$d` | 81 / 66 / 35 | positional integers (translations reorder) |
| `%1$@`, `%2$@` | 45 / 45 | positional strings |
| `%.2f` | 15 | fixed-precision number |
| `%%` | 45 | literal percent, e.g. `monitorAlerts.batteryBodyFormat` "Battery is at %d%%." |
| `%s` | 30 | **false positives**: not format strings. They are literal tokens in the screenshot file-name pattern help (`screenshot.fileNamePatternCaption`: "… %y, %year, %mo, %month, %d, %h, %mi …"). |

Rules for the TypeScript side:
* Only call the formatter where Swift calls `String(format:)`. A key ending in `Format` (or commented `// + count`) is a convention, not a guarantee, and the `%s`/`%y` help text shows that blindly formatting every string is wrong.
* Implement `formatSwift(fmt, ...args)` supporting `%@ %d %i %ld %lld %u %f %.Nf %n$@ %n$d %%`. Positional and sequential arguments can be mixed per string. Unit-test it against a few hundred real values from the JSON.
* Keep the printf syntax **verbatim** in the JSON rather than converting it to `{0}` or ICU syntax at extraction. It stays diffable against the Swift source, and the translators already work in this format.
* Island-table format keys, for reference: `notchActivities.sessionProgress`; `notchAgents` (13, e.g. `cachedFormat`, `leftFormat`, `planMultipleFormat`); `notchCalendar.weekNumber`; `notchClaudeSessions` (7, e.g. `leftRunningFormat` "%d left running", `dressUpFormat`); `notchEditor` (4); `notchMusicExtras.openNamedPlayer`; `notchWatch` (3); `clipboard.fileCountFormat`, `clipboard.clearRecentConfirmFormat`; `s.shelfSelectedFormat`, `s.mixerSystemOutputErrorFormat`, `s.mixerInputErrorFormat`; `scratchpad.padLimitFormat`, `scratchpad.deletePadMessageFormat`.

### 5.2 Plurals
There is no `.stringsdict` and no ICU plural syntax. Plurals are **separate fields** chosen in code:
* Field sets end in `Singular` / `Few` / `Plural` (or `…Format` for the many-form), e.g. `s.shelfTooltipFileSingular` "%d file", `shelfTooltipFileFew`, `shelfTooltipFilePlural` "%d files" (`LOC:755-770`).
* The form is selected by `AppLanguage.countAgreement` (`LOC:7-18`, `45-51`) in `ShelfTooltipStrings.form(for:)` (`SSupp:343-368`):
  * `oneAndMany` (12 languages): `|n| == 1` → one, else many.
  * `byLastDigits` (ru, uk): `n%100 ∈ 11…14` → many; else `n%10 == 1` → one; `n%10 ∈ 2…4` → few; else many.
  * `byWholeNumber` (sk): `n == 1` → one; `n ∈ 2…4` → few; else many.
* Port these three rules **literally** as `pluralForm(lang, n)`. Do **not** substitute `Intl.PluralRules`: it agrees for ru, uk and sk on integers (Intl names sk's last form "other", not "many"), but differs for French and Portuguese: CLDR puts both 0 and 1 in "one" for fr and pt, while the Mac uses "many" for 0. Other "plural" fields are simply single strings that read neutrally ("%d files" with a count).

### 5.3 Other text assembly
* Interpolation and concatenation in view code (§1.2). Search the Swift views for `"\(` and `+ " · "` when porting each component.
* Uppercasing in code: `l10n.s.launcherAddSection.uppercased()` (`UI/QuickLauncher/QuickLauncherView.swift:351`). Use `toLocaleUpperCase(lang)` (Turkish İ/ı).
* Language names are not localized per UI language; each language is shown in its own script (`displayName`).

### 5.4 Gaps
* `whatsAppDownloads` for 10 languages (`tr, ru, de, fr, it, ja, ko, zhHans, zhTW, zhHK`; 40 keys each) is built by calling a private Swift function (shape F). A static extractor cannot evaluate it without reimplementing the function; the compile-and-dump method (§6.2) can. This table is **not used by the island**.
* `notchClaudeSessions` is English in every language. The extractor writes the English values into all 15 files, which matches runtime behavior.
* Dictionary fields (`notchClaudeSessions.shells/hats/eyewears/extras`) are emitted as JSON objects (`{"clay": "Clay", …}`).
* **Not covered by the extractor** (none are island strings):
  * `Core/AlertSoundStrings.swift:65` is an `enum` with a private `names(for:) -> [String: String]` function (about 140 sound display names). It matches none of the six shapes.
  * `struct ShelfTooltipStrings` (`SSupp:327`) lives outside `Core/`. It holds no literals; it is assembled at runtime from `s.shelfTooltip*` fields (`UI/Shelf/ShelfTilesView.swift:463-478`), so nothing is lost.
* Accessors whose return type isn't a known strings struct are now **reported** as skipped, not dropped silently.

## 6. Extraction approach (prototype and verification)

### 6.1 Why not a line regex
A naive line regex (`^\s*(\w+): "(…)",?$`) happens to work on `NotchFilesStrings.swift` and `NotchStrings.swift`: it gave identical multisets, 240 and 1,365 values. It breaks on the rest of the codebase:
* tables written on one line (`FS:125-140`, Mixer);
* `.init(title: "…")` one-liners (GraphScale);
* tables inside the struct body (Clipboard, Mixer, Settings categories);
* aliases (`case .zhTW, .zhHK: return .zhTW`);
* English-only multi-case returns;
* delegation (`X.localized(language)`);
* dictionary values;
* escaped quotes.

It also cannot tell which language a value belongs to without tracking the surrounding `case`/`static let`.

### 6.2 The prototype: tokenizer + structural parser (no dependencies)
`windows/tools/i18n-extract/extract_swift_strings.py` (Python 3.9+, stdlib only) works in two passes:
1. **Tokenize** Swift properly: `//` and nested `/* */` comments; `"…"`, `"""…"""` and `#"…"#` literals with escapes, `\u{…}` and `\( … )` interpolation (flagged as unresolved); identifiers; punctuation.
2. **Parse** the six shapes from §1.2:
   * `struct *Strings { let f: T }` → the field list (and static tables or accessors inside the body);
   * `static let <ident> = Type(` / `.init(` → tables, with arguments split at top-level commas;
   * `static func <name>(_ language: AppLanguage) -> T { switch … case .a, .b: return … }` → per-language mapping (inline table, `.ident` reference, `Type.ident`, or `default:`);
   * delegation bodies `Type.func(language)` are resolved to the target accessor.
   
   A value is accepted only if it is a string literal, a `+` chain of literals, or a `[.case: "literal"]` dictionary. Anything else is **reported, never guessed**.

Output: one file per language, `en-US.json`, `pt-BR.json`, … `zh-HK.json` (named by `AppLanguage.rawValue`), shaped `{"<accessor>": {"<field>": "<value>"}}`. The accessor is the `FeatureStrings` function name (`notchFiles`, `clipboard`…), `s` for the main catalog, and `<Struct>.localized` for the few tables reached only through their own type. The run also prints a report: fields, values, unresolved values, problems (missing fields, extra labels, unresolved references) and format-specifier counts.

```
python3 -I windows/tools/i18n-extract/extract_swift_strings.py Sources/Vorssaint/Core --out <dir>
python3 -I windows/tools/i18n-extract/extract_swift_strings.py Sources/Vorssaint/Core --only NotchFilesStrings.swift NotchStrings.swift
```

**Test results**:

| Test | Result |
|---|---|
| `NotchFilesStrings.swift` (shape A, 16 fields) | 240 values, 0 problems |
| `NotchStrings.swift` (shape B, 91 fields) | 1,365 values, 0 problems |
| **Ground truth for both**: compile the two Swift files with `swiftc` plus a 20-line stub (`AppLanguage`, `enum FeatureStrings {}`), dump every language with `Mirror`, compare | **1,605 / 1,605 equal, 0 mismatches** |
| **Ground truth for the main catalog**: compile `LOC` + all 13 `LOCS/` files with a stub `DefaultsKey`, dump `Strings.localized(lang)` with `Mirror` | **1,074 fields × 15 = 16,110 / 16,110 equal, 0 mismatches** |

Both ground-truth checks are reproducible with `windows/tools/i18n-extract/ground_truth.sh` (macOS with `swiftc`).
| Whole `Core/` (88 files, 80 structs, 79 accessors) | 51,260 values, 0 unresolved literals; the only problems are the 10 WhatsApp builder languages (§5.4) |
| **Ground truth for all of `Core/`** (independent reviewer: all 88 files compiled with enum stubs for the Services types they reference, every accessor dumped with `Mirror`) | all 51,185 values emitted before the `-> Self` fix match exactly, 0 mismatches; field sets identical for every table. The 75 `SettingsNavigation` values added by the fix are plain literals of the same shape. |

**Verdict.** A structural parser over a real tokenizer is **reliable** for how these files are written: the source is uniform, machine-like and literal-only. Two compiled ground-truth checks gave zero differences. A regex is not reliable.

**SwiftSyntax** would also work and is grammar-exact, but it means building `swift-syntax` (a large package, minutes of build time, macOS or Linux toolchain only) to get the same information the tokenizer already yields for these six shapes. Not worth it unless the file style changes, e.g. if real interpolation appears.

**Compile-and-dump** (swiftc + `Mirror`) is the ground truth. It is the only method that also handles shape F (builder functions). But each strings file needs its compile-time dependencies stubbed: `ClawdShell`, `ClawdHat`, `NotchTimerPhase`, `DefaultsKey`, and so on. Use it as a **CI check** on macOS runners (dump and diff against the extractor's JSON), not as the primary extractor.

### 6.3 Recommended pipeline
1. `scripts/i18n:extract` runs the extractor into `windows/src/i18n/generated/<lang>.json`. The files are committed, and regenerated whenever the Swift side changes. This is a one-way flow: Swift stays the source of truth for shared strings.
2. Optionally `scripts/i18n:filter` keeps only the accessors the Windows UI imports (a static list, or a scan of `t("ns.key")` usages) to keep the bundle small.
3. `windows/src/i18n/overrides/<lang>.json` holds Windows-specific replacements for the about 80 Mac-specific island values (§4) and Windows-only strings (e.g. "Show in File Explorer", "Ctrl+1"). The overrides are merged over the generated files at build time. The override files need all 15 languages; a missing override falls back to the generated value, and the build logs it.
4. Runtime API: `t(ns, key)`, `tf(ns, key, ...args)` (with `formatSwift`), and `pluralForm(lang, n)` to choose between `…Singular/Few/Plural`. Build-time typing: generate `keys.d.ts` from `en-US.json` so a missing key is a type error. That keeps the Swift guarantee that every field exists.
5. CI checks:
   * every language has every key of `en-US`;
   * the printf specifiers of each translation match `en-US` (count, positions and types), which catches broken `%1$@` reorders;
   * on macOS, the compile-and-dump diff for the files that compile with simple stubs.

## Open questions / risks

1. **Source of truth after the fork.** If the Mac side keeps evolving, re-extraction must be repeatable. The extractor depends on the six shapes staying as they are. A new shape (interpolation in a table, a computed property) is reported as "unresolved", not silently dropped. Keep the CI diff.
2. **Windows wording.** About 80 island values mention Mac, Finder, ⌘ or System Settings. They need professional translation in 14 languages. Machine replacement would break grammar (case endings in ru/uk/sk/de; word order in ja/ko).
3. **Which `s` keys the island uses** was estimated by name-matching (about 134). Shipping all 1,074 `s` keys (about 85 KB per language) removes the risk at negligible cost. Recommended.
4. **WhatsApp tables** (shape F) are not extracted statically. They are irrelevant to the island; only a port of the WhatsApp feature would need the compile-and-dump route.
5. **Plural rules must stay custom** (`oneAndMany` treats 0 as "many" in fr and pt). Using `Intl.PluralRules` would silently change French and Portuguese output.
6. **Date and number formatting.** The Mac mixes the UI language with the system region, hour cycle and week start. On Windows those come from `GetLocaleInfoEx`. Make sure they are re-read on `WM_SETTINGCHANGE`; otherwise the island shows stale 12/24 h formats until restart.
7. **Turkish casing and CJK width.** Uppercase only with `toLocaleUpperCase(lang)`. The Mac measures text with AppKit fonts for layout decisions (e.g. clipboard open height, capture-controls title width); on Windows, measure with canvas `measureText` in the same font, Segoe UI Variable or the font the shell spec chooses, or wide glyphs will mis-size cards.
8. **Font fallback.** SF Pro has no Windows equivalent; zh-Hans, zh-TW, zh-HK, ja and ko need explicit font-family fallbacks (Microsoft YaHei UI, Microsoft JhengHei UI, Yu Gothic UI, Malgun Gothic), or WebView2 may choose inconsistent glyphs for HK and TW.
