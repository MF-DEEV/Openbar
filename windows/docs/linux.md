# Linux (X11 and Wayland)

The island runs on Linux under X11 (tested on XFCE with xfwm4 and picom). On Wayland the island itself works on compositors with layer-shell (sway, Hyprland, labwc, river, KDE Plasma), and GNOME runs it through XWayland; much of what reaches other apps is still X11 only, see [Wayland](#wayland).

## Install

The [Linux releases](https://github.com/MF-DEEV/Openbar/releases?q=linux&expanded=true) carry a `.deb` (Debian, Ubuntu, Mint), an `.rpm` (Fedora, openSUSE) and an AppImage (anything else), each for x86_64 and Arm64. They are built on Ubuntu 22.04, so they need glibc 2.35 or later.

```sh
sudo apt install ./Openbar_<version>_amd64.deb      # Debian, Ubuntu
sudo dnf install ./Openbar-<version>-1.x86_64.rpm   # Fedora
chmod +x Openbar_<version>_amd64.AppImage && ./Openbar_<version>_amd64.AppImage
```

The packages pull in WebKitGTK and GTK and recommend what the extras use (`pactl`, `tesseract`, `ffmpeg`); the AppImage expects them on the system. Start Openbar from the applications menu, then start `claude` in a terminal.

## Build

You need [Bun](https://bun.sh), [Rust](https://rustup.rs) and the Tauri system libraries (`webkit2gtk-4.1`, `gtk3`, `libayatana-appindicator`, `librsvg`, `openssl`, `xdotool`). To run it, reading text from the screen needs `tesseract` (with the data of your languages) and sound also needs `pactl` and `parec` (the `libpulse` package on Arch and Fedora, `pulseaudio-utils` on Debian and Ubuntu, with PulseAudio 16 or later or PipeWire's pulse server)), and the screen recorder needs `ffmpeg` (built with x11grab, libx264, AAC and PulseAudio input, as distributions build it). Then, in `windows`:

```sh
bun install --frozen-lockfile
bun run build
cd src-tauri
cargo build --features tauri/custom-protocol   # embeds ../dist; without it the app loads the dev server
```

Packages: `bun run tauri build` makes the `.deb`, `.rpm` and AppImage (`tauri.linux.conf.json` sets them in place of the Windows installer). The released ones come from `tools/linux-packages.sh`, which builds them in a clean Ubuntu 22.04 container, once per architecture, from the repository root:

```sh
docker run --rm --platform linux/amd64 -v "$PWD:/src:ro" -v "$PWD/dist-linux:/out" \
  ubuntu:22.04 bash /src/windows/tools/linux-packages.sh
```

`linux/arm64` builds the Arm packages; on an Apple silicon Mac, a Linux VM with Rosetta (Lima's `--rosetta`) runs the x86_64 container at near native speed. Linux releases are tagged `linux-v<version>`.

## What works

- The island window: transparent, always on top, a dock window that takes no focus. The window is cut to the island's shape (XShape), so clicks anywhere else go to the windows below, which also works under xfwm4. A compositor that blurs behind windows (picom) blurs the whole cut, so the cut follows what is drawn, not where the island is going, and is exactly the painted shape (a notch's ears included, with no margin), or the blur would show as a frosted outline around the island; the round buttons grow in without fading.
- Claude Code sessions, read from `~/.claude/sessions` through `/proc`. Hooks reach the island over a socket in `~/.openbar` (in the temp folder when the home folder's path is too long for a socket address).
- Codex sessions the app server does not list (`sessions/codex/local.rs`): a Codex running in a terminal, found as a process named `codex` and tied to its rollout under `$CODEX_HOME/sessions` (`~/.codex` by default), gets a row as on Windows. Open raises its terminal, and a reply is typed into tmux, kitty or WezTerm as a paste, the way it is for Claude Code. Checked with a stand-in process and a rollout made to the format; no Codex was available to run it against.
- Open and Reply (tmux, kitty and WezTerm are covered by tests against stand-in programs, not run against the real ones): Open raises the terminal's window through the window manager (`_NET_ACTIVE_WINDOW`). Replies go into tmux (`$TMUX`, `$TMUX_PANE`; the pane must be on the session's own terminal, since an editor opened from a pane keeps both), zellij (`$ZELLIJ_SESSION_NAME`, `$ZELLIJ_PANE_ID`; the session must run under that zellij server; `hosts/zellij.rs`, shared with Windows), kitty (needs `allow_remote_control` and `listen_on`; the window must list the session's process), WezTerm (`wezterm cli`) and VS Code, Cursor, Antigravity and Windsurf through the bridge extension. Any other terminal is raised, not typed into.
- The island hides while a fullscreen app is active (`_NET_WM_STATE_FULLSCREEN`), and "All displays" puts a mirror on each other monitor. The same look at the active window tells whether you are in an app, as Windows reads its foreground window: the island presents itself (a waiting session, a notice) only once the desktop, a panel or one of Openbar's own windows has been in front for 750 ms, and a session page collapses when you go to an app (`linux/fullscreen.rs`). On a Wayland compositor Openbar can't ask (labwc, river) it presents as it always did.
- Keep windows below the island (Settings › Behavior, on by default): the closed island's strip at the top of its display is kept out of the work area, as a top panel's is, so a maximized browser starts below the island and its tabs stay in view. An invisible dock window per display holds a `_NET_WM_STRUT_PARTIAL` as tall as the closed island (`room.rs`); the strip follows the display choice (the island's display, or every display for "Cursor" and "All displays") and goes away with "Hidden until hover", with the setting off, and when the app quits, since the X server drops the windows of a client that is gone. A display with another one above it gets no strip, because a strut counts from the top of the whole screen.
- Now playing (`media.rs`): any player on the session bus that speaks MPRIS (Spotify, VLC, Rhythmbox, a browser tab, ...), with its cover, seek, shuffle, the source menu and Open player (raises the player, or starts it from the applications menu). The Spotify queue is read through Windows accessibility and has no Linux counterpart. Covers come from files and HTTPS, through the web view's own HTTP library (libsoup).
- Sound (`audio/`): the Mixer and Controls over the sound server (PulseAudio, or PipeWire's pulse server) through `pactl`: the output's and microphone's level and mute, the default device, every app that plays with its own level, Mic Mute, audio priority, the headphone guard, the output switcher and the finer volume keys. An app counts as playing while its stream is not paused. The Music page's player volume and the spectrum next to the song work too; the spectrum records the player's own stream with `parec`. The microphone indicator shows when an app records from a microphone (it reads the server's lists and never records, so it has no level meter), and Discord's own mute and deafen (`linux/discord_voice.rs`): the Mute and Deafen buttons of Discord's user panel are read through AT-SPI while its window is shown, and until then the state Discord saved at its start. As for answering Discord, it must have started with accessibility on. Windows also follows Discord's mute shortcuts while it is hidden; the key codes Discord saves on Linux are not known, so a shortcut pressed then shows once its window is seen. Checked with an Electron stand-in that has Discord's two buttons, not with Discord.
- Icons and names (`shell.rs`): the icon theme and the desktop entries give app icons, file icons and thumbnails, and the system monitor opens from the System page.
- Power (`battery.rs`, `power_saver.rs`, `session_lock.rs`, `keep_awake.rs`): the machine's own batteries from `/sys/class/power_supply` (charge, charger, rate, time left, wear and cycles; a mouse's battery or a UPS is left out), the energy saver as power-profiles-daemon's `power-saver` profile, the lock and unlock of the session (from systemd-logind's `Lock`, `Unlock` and `LockedHint`, a screensaver service's `ActiveChanged`, or a screen locker program such as `xsecurelock` or `i3lock` starting and ending), which with the minutes without input (the X server's screen saver extension, else GNOME's idle monitor or logind's idle hint) gives the "while you were away" card, and Keep Awake through logind's inhibitor and the desktop's power manager.
- Brightness (`brightness.rs`): a panel's backlight, written through logind, and external displays over DDC/CI with `ddcutil` (which needs the `i2c` group).
- Quick toggles (`toggles.rs`): lock the screen, turn the display off (X11 power management), start the screensaver, empty the trash, and dark mode on GNOME-family desktops. Hidden files, desktop icons and ejecting disks differ too much between desktops and are not offered.
- Update check (`src/updates/`, the same page code as on Windows): the web view asks GitHub's releases list for a newer `linux-v<version>` tag (the Linux packages' own; Windows reads `windows-v`), once after start and every six hours, and a newer one is offered in a notice, in the island's menu and in Settings › General. Nothing is downloaded, so it only opens the release page.
- Notifications (`notifications.rs`): there is no list of other apps' notifications to read on Linux, so the island listens to the calls apps make to the notification service (a monitor connection to the session bus, as `dbus-monitor` does; the desktop's own popup still shows). It keeps the title, text and icon of what arrives while it runs, folds an app's updates of one notification into one entry, and leaves out transient ones and the volume and brightness displays. Open starts the app the notification came from. Discord messages can be answered from the island (`discord_reply.rs`, see [notifications](notifications.md)); Discord must have started with desktop accessibility on.
- System (`system_monitor.rs`): CPU, memory (with swap, cache and zram), network, disk space and activity, the GPU (`nvidia-smi`, or an AMD card's busy file), battery, uptime and connected USB and Bluetooth devices, read from `/proc`, `/sys` and BlueZ, with the CPU, memory and GPU (NVIDIA) process lists grouped by program. Network activity by app (`linux/net_process.rs`) comes from the kernel's socket diagnostics (`NETLINK_SOCK_DIAG`, what `ss -ti` reads): each TCP connection's bytes received and acknowledged, with no privileges, and `/proc/<pid>/fd` for the process holding it; the first reading is the baseline. Only your own processes can be looked into, and UDP keeps no byte counts there, so other users' apps and QUIC are not counted. Power by process needs privileges (RAPL is root's), so that list says it is unavailable.
- Clipboard (`clipboard/`): the history of copies (text, files and pictures, in that order of preference) through GTK's clipboard, which tells when its owner changes. A copy a password manager marks as secret (`x-kde-passwordManagerHint`) is left out, the app a copy came from is the clipboard's owner or else the window in front, and Paste brings forward the window the island took the keyboard from (else the one in front) and types Ctrl+V (Ctrl+Shift+V in a terminal) into it through the X server's test extension, the keys 10 ms apart so a busy terminal takes them. Needs a window manager that keeps `_NET_ACTIVE_WINDOW`, as every desktop one does.
- Images in a reply (`sessions/attachments.rs`): the paste button in a session's reply box reads the same GTK clipboard, a picture (PNG, as screenshot tools copy it) or the image files a file manager copied (at most five, 20 MB each), and the reply types their paths into the terminal like any other image.
- Calendar (`calendar.rs`, `ics.rs`): Linux has no one store of appointments, so the system's events are read from calendar files: `.ics` files in `~/.local/share/openbar/calendars`, Evolution's local calendars, and the folders vdirsyncer and khal keep (a folder of `.ics` files is a calendar, named and colored by its `displayname` and `color`). Repeating events are expanded (daily, weekly, monthly and yearly rules with their usual parts, exceptions and changed occurrences). Events made in Openbar work as on Windows. Clicking any other event opens the desktop's calendar app (the default for `text/calendar`), never with the calendar file, which it would import; an event of one of Evolution's local calendars opens in GNOME Calendar on that event (`--uuid <source>:<uid>`, the built-in calendar's source being `system-calendar`), else in Evolution. Evolution Data Server, KDE's Akonadi and online accounts are not read; syncing them to files (vdirsyncer) is how they get in.
- Screen capture (`capture/`, `ocr.rs`): the screenshot, Copy text from screen and colour picker tools take the picture of the screen from the X server (`GetImage` of the root window), find the display under the pointer with RandR and the window under a point from the window manager's stacking list, and put pictures and text on the clipboard. Reading text uses Tesseract (`tesseract` with the language data of your locale, and English). A screenshot is dragged out of its preview as a file, the way a Shelf tile is. Sharing is a Windows feature and is not offered.
- Background sessions (`sessions/background.rs`): Claude Code's and Codex's own commands run with no window (`claude agents` lists the background agents); a new session or an attach opens in the first terminal found (`$TERMINAL`, then GNOME Terminal, XFCE Terminal, Konsole, kitty, Alacritty, WezTerm, foot and others); a reply to a background session is typed into `claude attach` on a pseudo-terminal nobody sees.
- Alerts: the sound a waiting session makes (Settings › Content › Sessions) can be Openbar's chime or a sound of the freedesktop sound themes (`sounds/<theme>/stereo` under `$XDG_DATA_HOME` and `$XDG_DATA_DIRS`, the volume and speaker tests left out; the person's own folder first), played the same way. The timer's and Watch's chime is played through `paplay`, `pw-play`, `aplay` or `ffplay`, whichever is found first, and the timer counts time since boot (`CLOCK_BOOTTIME`), so a timer that ran out while the PC slept rings when it wakes.
- File actions (`files/shell.rs`) and Downloads (`downloads.rs`): Open starts a file with the app the desktop has for its type, Open With lists the apps that can open every selected file, Show in file manager asks `org.freedesktop.FileManager1` to select the files (or opens the folder when no file manager answers), and Delete moves a file to the trash. The Shelf's items, pins and ZIP archives are plain file handling. Dragging works through GTK's own drag and drop on the island's web view (`shelf.rs`): files, links and text dragged onto the island go on the Shelf, as they do through Windows' drop target, and a tile is dragged out as the files (a URI list, which file managers, editors and browsers take) or as text (a link goes out as its address). A drag that starts in the page itself, such as a text selection, is left to the page. The downloads list watches the desktop's Downloads folder and the folder each Chromium browser profile or Firefox profile is set to save in, and follows the browsers' temporary files (`.crdownload`, `.part`). A Chromium profile's own record of what it is downloading (its `History` database) adds the size the file is going to have, so the row has a percentage, whenever SQLite can open the database: Chromium keeps it locked while the profile is open, so there the list follows the file as it grows, as it does for Firefox. Sharing is not offered, since Linux has no Share sheet.
- AI Agents usage (`agent_usage/`): Claude Code's, Codex's and Copilot's logs are read from `~/.claude`, `$CLAUDE_CONFIG_DIR`, `~/.config/claude`, `~/.codex` and `~/.copilot`, and a Claude session counts as running by its record in `sessions/`, which Claude Code on Linux writes with the machine and namespace in its `pidDomain`. Checked with `--agents-probe` against this machine's own logs (106 files, 26 thousand records); Codex and Copilot are covered by the shared parser's tests, there were no logs of theirs to read. The plan limits come from the vendors' command line tools and were not tried. OpenCode's database (`opencode.db` in `$XDG_DATA_HOME/opencode`, `~/.local/share/opencode` by default) is read through libsqlite3, which the app loads when it first needs it (`sqlite.rs`) and does not link; this machine has no OpenCode, so the reader is covered by tests on databases made to its own queries, not by a real one. The daily price list is fetched through libsoup (`raw.githubusercontent.com`, no redirects, 256 KiB at most) and kept in `~/.config/com.openbar.island/agent-prices.json`; the prices built in serve until it arrives.
- Language and regional formats (`locale.rs`): the UI language follows `LC_ALL`, `LC_MESSAGES` or `LANG` (with `LANGUAGE` leading, as gettext has it, and the C locale meaning English), the region and 12 or 24 hour clock follow `LC_ALL`, `LC_TIME` or `LANG` (the clock format is the C library's, so the locale must be installed), and the week starts on Sunday in the regions that start it so, Monday elsewhere.
- Screen recorder (`recorder/`): the Record tool grabs the chosen area with `ffmpeg` (x11grab), takes the system's sound from the default output's monitor and the microphone from the default input, mixes them, and writes an H.264 and AAC MP4 into the Videos folder. Stopping tells ffmpeg to close the file, and a file it could not close is not offered. The island is part of the screen, so it is in a recording when it is in the area (X11 cannot leave a window out of a capture).
- Voice replies (`voice/`, `linux/voice.rs`): the microphone button next to Reply, as on Windows. When there is no microphone to read, Open Settings next to the message opens the desktop's sound settings (GNOME, KDE, Cinnamon, MATE), else PulseAudio's volume control on its input devices. `parec` reads the sound server's default input at 16 kHz mono and whisper.cpp, built into the app, turns it into words on this PC; no audio is sent anywhere. The speech model (60 MB) is downloaded from Settings → Sessions → Voice replies, through libsoup, and kept in `~/.config/com.openbar.island/models`. The hold-to-talk shortcut works on X11 (a Wayland compositor does not report the key's release). Building needs `cmake`, a C++ compiler and `libclang` (`libclang-dev` on Debian and Ubuntu, `clang` on Arch).
- Speed test (`speed_test.rs`): latency, download and upload against Cloudflare's public speed endpoints (the ones speed.cloudflare.com uses), through libsoup, the web view's own network stack, so the system's proxy and TLS settings apply. A run moves as much as the link carries in about ten seconds, as on Windows, and the upload is zeros.
- Watch (`linux/watch.rs`): the capture overlay's area becomes a live activity as on Windows. The window under the middle of the area is followed wherever it goes and read through the Composite extension, so a window another one covers is read as it is drawn (a server without the extension reads it where it is on the screen); a part of the desktop is read from the root window, and the island is in it when it covers it, since X11 cannot leave a window out of a picture. A hidden or minimized window pauses the watch. The number format (decimal mark, space between thousands) follows `LC_ALL`, `LC_NUMERIC` or `LANG`, and a watch that ends while the island is hidden is posted through the notification service. Checked on a nested X server with a covered window, not with a compositor such as picom, and the text is read by the same `tesseract` as the OCR tool.
- Global shortcuts, tray icon (its menu; a plain click does not open Settings, the tray protocol has no click event), launch at login (`~/.config/autostart/openbar.desktop`).
- The Scratchpad's Save as file shows GTK's save dialog, starting in the Documents folder. A worktree's Open folder opens it in the desktop's file manager.
- Texts that name Windows on Windows have their own Linux wording ("Start at login", "Show in Files", "Open System Monitor", what the memory figures mean on Linux), kept in each language's overrides under the same key plus `Linux`, which `t()` picks on Linux.
- Settings and caches live in `~/.config/com.openbar.island` and `~/.cache/com.openbar.island`.

## Wayland

Wayland gives an app no say over where its window goes or what stays on top, and nothing about other apps' windows, the pointer outside its own window, the clipboard while another app has the keyboard, or the screen (#252). What the island needs of that comes from the compositor's own protocols and from small tools that speak them.

- **The island** (compositors with layer-shell: sway, Hyprland, labwc, river, KDE Plasma; checked on sway): with `gtk-layer-shell` installed (`libgtk-layer-shell0` on Debian and Ubuntu, `gtk-layer-shell` on Fedora and Arch; the packages recommend it, the AppImage expects it), the island is a layer surface over the whole display, above other windows and panels (`linux/layer.rs`, looked up when the island is made, not linked). It takes the pointer only where the island answers to it (its input region, in place of XShape), knows where the pointer is only while it is over the island, and catches every click while it is open, so a click beside the open island closes it and does not reach the window under it. Keep windows below the island holds an exclusive zone on the island's display with an empty surface of its own. The island stays on its display: Follow pointer and All displays need the pointer's place on the screen, which Wayland does not give, and act as Primary.
- **Other apps' windows** (`linux/wm.rs`): sway and Hyprland are asked over their IPC sockets (`$SWAYSOCK`, `$HYPRLAND_INSTANCE_SIGNATURE`); on KDE Plasma a small KWin script, loaded over D-Bus, reports the windows to Openbar on the session bus whenever they change, and a one-line script raises one (`linux/kwin.rs`, Plasma 5 and 6). That gives the window in front, whether it is fullscreen (the island hides as on X11), Open raising a session's terminal, and the display the capture tools use (the focused one). Other compositors (labwc, river) have neither, so these do nothing there.
- **Paste** (sway, Hyprland, KDE): the window the island took the keyboard from is focused through the compositor and Ctrl+V (Ctrl+Shift+V in a terminal) is typed with `wtype` (the virtual keyboard protocol: wlroots compositors and Hyprland), else with `ydotool`, whose daemon `ydotoold` must be running with access to `/dev/uinput` (KDE has no virtual keyboard for apps).
- **Clipboard history**: Openbar hears each copy through the data-control protocol sway, Hyprland and KDE give clipboard managers (spoken in-process, `linux/wl_clipboard.rs`), and reads and writes it with `wl-paste` and `wl-copy` (wl-clipboard). KWin 5.27 names a copy's types in garbled bytes; text is still read there, files and pictures are not. A copy is credited to the app in front where the compositor says which one that is.
- **Screenshot, Copy text from screen, colour picker and Watch of a part of the display**: the picture comes from `grim` (wlroots' screencopy, so sway, Hyprland, labwc, river), on KDE from Spectacle (`spectacle --background`), and the selection overlay is a layer surface that takes the keyboard. Watch of a single window is X11 only: an area picked on Wayland is a part of the display. The overlay itself could not be seen in the test VM (it does not show there on X11 either, a WebKit issue without a GPU); the picture, its area and the display were checked.
- **Screen recorder**: `wf-recorder` takes the picture and hands raw frames to ffmpeg through a pipe, so the sound, the file and Stop work as on X11 (wlroots compositors and Hyprland; not KDE).
- **Global shortcuts**: a Wayland compositor keeps the keyboard to itself, so bind the keys in its configuration to `openbar --shortcut <keys>`, which tells the running Openbar the keys were pressed: the island's shortcut, the sound output switcher, the volume keys, and Ctrl+Y, Ctrl+N and Ctrl+T while a session asks for permission. For sway:

  ```
  bindsym Ctrl+Alt+Space exec openbar --shortcut Ctrl+Alt+Space
  bindsym Ctrl+y exec openbar --shortcut Ctrl+Y
  ```

  Hold-to-talk for voice replies needs the key's release and has no such binding (the microphone button works). The shortcuts of the island's sections (Ctrl+Alt+C and the like) work while the island has the keyboard, as on X11.
- **GNOME**: Mutter has no layer-shell, so on a GNOME Wayland session the app sets `GDK_BACKEND=x11` and runs through XWayland as on X11, unless `GDK_BACKEND` is set. The island then sees, raises and types into XWayland apps only, and captures what XWayland shows.
- **Still X11 only**: Watch of a window, answering Discord from a notification, and turning the display off. Without `gtk-layer-shell`, or on a compositor without layer-shell that is not GNOME, the island is an ordinary window.

Checked on sway 1.9 nested on Xvfb in an Ubuntu 24.04 VM: the island, its room, hover, open and close, fullscreen hiding, Open, Paste into foot, the clipboard history, the picture of an area, a recording and `--shortcut`. On KWin 5.27 nested the same way: the island above windows, open by click, fullscreen hiding, Open and the clipboard history. Not tried: Spectacle's picture and `ydotool` on KDE (the VM has no GPU for KWin's screenshot effect and no input KWin reads from `/dev/uinput`), Plasma 6, Hyprland, labwc, a real GNOME session, scaled displays.

## Where the code is

Everything Linux does differently is in `src-tauri/src/linux/`, a file for each piece of Windows code it stands in for: the window (`island.rs`, with `room.rs` for the strip windows keep out of, and `layer.rs` for the layer surface on Wayland, `wm.rs` and `kwin.rs` for other apps' windows and `wl_clipboard.rs` for the clipboard and typed keys there), fullscreen (`fullscreen.rs`), launch at login (`autostart.rs`), processes from `/proc` (`process.rs`), terminals and editors (`hosts.rs`, `tmux.rs`, `kitty.rs`, `wezterm.rs`, `x11.rs`, `command.rs`, `ide.rs`), session records (`sessions.rs`), hooks (`hooks.rs`), the XDG folders (`paths.rs`), now playing (`media.rs`), power and brightness (`battery.rs`, `power_saver.rs`, `session_lock.rs`, `keep_awake.rs`, `brightness.rs`, `toggles.rs`), notifications (`notifications.rs`), the System page (`system_monitor.rs`), the clipboard (`clipboard.rs`, `gtk_main.rs`), the calendar (`calendar.rs`, `ics.rs`), screen capture (`screen.rs`, `ocr.rs`), background sessions (`background.rs`), the alert chime (`sound.rs`), sound (`audio.rs` and `pulse.rs`, with `microphone.rs` and `music_levels.rs` for the indicator and the spectrum), icons (`shell.rs`, `image.rs`, `desktop.rs`) and the file actions, downloads folders and dragging (`files.rs`, `downloads.rs`, `shelf.rs`), the locale (`locale.rs`), the screen recorder (`recorder.rs`), the speed test and the price list (`speed_test.rs`, `prices.rs`, with `net.rs` for what they share), network activity by app (`net_process.rs`), the accessibility bus (`atspi.rs`, read by `discord_reply.rs` and `discord_voice.rs`) and the SQLite calls of the OpenCode reader and the downloads list (`sqlite.rs`). The Windows modules only hand over to these with `cfg(target_os = "linux")`, and the code Windows compiles is otherwise as it was. A new Linux piece is a new file there and one hand-over where the Windows module has its own.

## NVIDIA

WebKitGTK cannot back its GBM buffers on the proprietary driver and leaves every page blank. The app sets `WEBKIT_DMABUF_RENDERER_FORCE_SHM=1` when `/proc/driver/nvidia/version` exists, unless one of the `WEBKIT_DMABUF_RENDERER_*` or `WEBKIT_DISABLE_DMABUF_RENDERER` variables is already set. `WEBKIT_DISABLE_DMABUF_RENDERER=1` alone does not draw the island's body.

## Without 3D acceleration

WebKit gets its GPU buffers for a window through DRI3. On an X server that has none (Xvfb, a VM without 3D) the island stays invisible, so the app sets `WEBKIT_DISABLE_COMPOSITING_MODE=1` when the server lacks DRI3. Set `WEBKIT_DISABLE_COMPOSITING_MODE` yourself, `0` to keep the default, and the app leaves it alone.
